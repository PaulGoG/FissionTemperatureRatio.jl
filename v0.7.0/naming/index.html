Naming

Each quantity has one name, used wherever it appears: Julia identifier, struct field, configuration key, directory name, file name, column header, figure label and prose. The spelling depends on the context (heavy_mass_max in a configuration, A_H in a path), but the quantity named is the same.

A name describes what it holds: a table of R_T against A_H is R_T_vs_A_H, a type carries no Data suffix, and no column is called value.

This page lists the vocabulary as this package uses it. The retrieval that supplies the experimental input and the prompt emission codes that read the output use the same quantity table and the same file layout.

Two registers

symbolA_H, nudirectory names, file names, column headers, figure labels, Julia identifiers of the equations

A configuration is edited by hand, so its keys spell a quantity out. Paths and headers carry the symbol, as the literature does. Accordingly FragmentationSettings has a field heavy_mass_max, named after the key it is read from, and a ratio curve has a field A_H, named after the symbol of the equations.

Uncertainty

The uncertainty of a quantity is named <quantity>_uncertainty and placed immediately after that quantity, as in A nu nu_uncertainty. A bare uncertainty column is not used, because it does not say which quantity it belongs to. Julia code uses the symbol instead (σν, σY).

Unicode is used only where an identifier is a symbol of the governing equations (ΔZ, σ_Z, ν, Zₚ, A₀, R_T), so that the implementation reads like the formulation. The exported API stays ASCII-typeable: every public function and every keyword argument can be typed without a compose key.

Function names begin with one of six verb prefixes (read_, write_, build_, load_, run_, is_); a function that fits none of them is named for what it returns. read_<thing> returns the type <Thing>, so the reader of a MassExcessTable is read_mass_excess_table. load_<thing> reads and validates, hence load_configuration.

Type names carry no Data suffix: a type holding multiplicities is Multiplicity, one holding mass yields is MassYield, one holding the charge polarization and dispersion is ChargeDistribution. Table is kept only for a lookup table keyed by nucleon number. The piecewise-linear fit of one measurement is a SegmentedFit, and the temperature ratio extracted through it is an ExtractedCurve. The tabulated curve that a consuming code reads is FissionFragmentsDomain's SegmentedCurve, a different object under a different name.

The fragmentation domain, the nuclides and systems, the mass table, the charge models, the level density models, the relation between R_T and E*_H/TXE, the mass yield and the run record are FissionFragmentsDomain's, and keep its names here; this package adds methods to its functions and defines no second function under the same name.

A package has one result type, named <Verb>Result; here it is ExtractionResult. A generic RunResult would collide with the same name in a consuming code when both packages are loaded.

Abbreviations are used only where the field uses them (TKE, TXE, BSFG, GC, EXFOR, AME, RIPL, sf, BIC). Programming abbreviations such as err, param, calc, val, idx, num, cfg and pts are not used. The only short forms are the seven readable tokens of a run identifier, described below.

Configuration files

A configuration is named <system>.toml, the token that names the data directories it reads and the output directory it writes. A system carrying more than one configuration would name them <system>_<case>.toml; none does. The test suite checks each file name against the system the file declares.

Sections are [system], [fragmentation], [level_density], [multiplicity], [yield], [segments], [retrieval] and [output]. A key is not prefixed with the name of its section: [level_density] model, not level_density_model. Every key, with its type, bounds and default, is listed under Configuration.

The comment of a key states what the key is, in one short line, its enumerated choices where it is constrained, and its bounds and unit. Physics and run rationale belong in the documentation. The loader enforces what the comment declares.

A key whose value follows from other keys is not in the file: the reaction code follows from the entrance channel, and the fissioning nucleus from the target and the channel.

subdirectory names a folder under a root, and directory names a root path. A configuration therefore says [multiplicity] subdirectory = "U233_nth/nu_vs_A", under the data root, and the root itself is an argument of load_configuration.

significant_digits counts significant figures, not decimal places: a ratio near unity and an uncertainty near 10⁻⁵ appear in the same table, and a fixed number of decimals would not give both the same precision.

The system identifier

One token for a fissioning system, used as a directory name, a configuration file name and an output directory:

<ElementSymbol><A>_<entrance channel>

The channel is spelled as in the literature, not as a reaction code: Cf252_sf, U235_nth, U235_nres, U233_nth, Pu239_nth. A reaction code such as 0f belongs in the run record. The channel also distinguishes a thermal from a resonance run of one system, which the reaction code n,f does not.

FissionFragmentsDomain's system_label returns that token. The typeset form for a figure or a caption, ²⁵²Cf(sf) or ²³³U(nth,f), is returned by a separate function, system_notation.

The atomic mass evaluation and the Gilbert-Cameron shell corrections are the ones FissionFragmentsDomain ships, named "ame2020" and "gilbert_cameron_1965" in a configuration.

There is one directory per system, one subdirectory per measured quantity and one file per measurement. The directory names the quantity and the file name carries the provenance, so that every curve can be traced to its archive accession.

A tabular file is named <quantity>_vs_<abscissa>[_<abscissa>]. The extension states the format only: .dat whitespace-separated, .csv comma-separated, .toml metadata. The nuclide is in the path, never in the extension.

One header line, ASCII, abscissae first, then the ordinate, then its uncertainty:

A nu nu_uncertainty
A Y Y_uncertainty
A TKE TKE_uncertainty
A dZ sigma_Z
A_H,R_T,R_T_uncertainty

No column is named value: a column named for its quantity is readable without the file name, which matters most for the files that cross a package boundary.

Readers take columns by position, not by header text, so renaming a header upstream or downstream changes nothing. The docstring of every reader in this package states this.

Output files and run identifiers

A run is one directory, and the directory carries the run identifier. Tables go under the system in data/sims/, figures under the system in plots/:

An output follows the same <quantity>_vs_<abscissa> rule as an input, so it can be fed back in without translation, and a table name carries the quantity, the abscissa and the dataset, nothing more. <dataset> is the stem of the input file, <accession>_<Author>_<year>, so the archive accession is in the name of every file of a measurement; the trend's files carry its label, systematic_trend. A label, Author year, is the display name and the key that selects a curve in the manifest, and takes the accession only where two datasets would share it:

The ratio tables have the headers A_H,r_nu,r_nu_uncertainty and A_H,R_T,R_T_uncertainty, the pivot table included; in the point-by-point tables an uncertainty the measurement does not quote is an empty field, never zero. segmented_curves_<run>.csv has the columns label, accession, kind, pooled, segments, pinned_at_symmetric_split, first_A_H, last_A_H, pairs, measured_points, coverage, reduced_chi_squared, chi_squared_over_expectation, weights_imputed, range_mean_R_T, range_mean_R_T_uncertainty, deviation_autocorrelation, all dimensionless. chi_squared_over_expectation equals reduced_chi_squared for a dataset curve, and the last, filled for the systematic trend only, is the ρ its covariance was formed with.

total_average_R_T_<run>.csv has the columns segmented_curve, mass_yield, R_T, R_T_uncertainty, R_T_uncertainty_independent_points, R_T_uncertainty_leave_one_out, R_T_leave_one_out_min, R_T_leave_one_out_max, yield_fraction, R_T_one_more_segment, R_T_two_more_segments. The three leave-one-out columns and the last two are filled for the systematic trend only. For the trend of a run that made the refits, R_T_uncertainty takes the larger of the term propagated from the fit covariance and the jackknife of the average over the refits with half of the pooled datasets left out, before the term of the yields is added. R_T_uncertainty_leave_one_out is the delete-one jackknife of the average over the leave-one-out refits: a diagnostic of how far the average rests on single datasets, and the jackknife R_T_uncertainty takes only for a pool of two or three. R_T_uncertainty_independent_points is the approximation of the published tables over the tabulated points of a curve, formed from their tabulated uncertainties: for a trend that carries a jackknife, from the larger of the two at each mass number.

leave_one_out_<run>.csv has the columns dataset_left_out, accession, mass_yield, R_T, segments, breakpoints, reduced_chi_squared, outcome, one row per dataset or experiment left out and yield distribution. The labels of an experiment are joined by +; its accessions, like the breakpoints, are separated by spaces.

dataset_diagnostics.csv has the columns dataset, accession, points, pairs, first_pair, last_pair, coverage, outside_physical_range, complement_sum, complement_spread, without_uncertainties, qualifiers, pooling_weight, flagged, pair_sum_deviation, scale_consistent, pooled, pooled_with, exclusion_reason, segmented_curve, curve_flagged, curve_flag_reason. outside_physical_range counts the complete pairs left out because their r_ν falls outside (0, 1). segmented_curve reads "segmented curve" or states why there is none: no complete pair, coverage below the floor, or no fit and the reason. write_results refuses a run whose identifier would make one of those names longer than the 255 bytes a file system admits.

The manifest, the curve table, the total averages and the leave-one-out refits repeat the identifier in their names; the per-curve ratio tables do not, and are found through the manifest. A consuming code stages the whole run directory and selects the manifest by its manifest_ prefix, and the token keeps a staged copy attributable after it has left data/sims/. A run directory holds exactly one. Consuming the output describes the manifest. The systematic-trend curve is labelled systematic_trend, the same token as its kind.

A run-identifier parameter is the configuration key it came from, by section and key as the file spells it, segments.max_segments. Every key that changes the result of the run is a parameter; the system is not, since it names the directory the identifier sits in, nor are [retrieval], a guard on the inputs, and [output], which changes how a number is rendered and not the number. A key that cannot change this run's result is none of its parameters either: the Gilbert-Cameron keys of a back-shifted Fermi gas run, windows_apply_to_datasets without windows, an input that is not given. Only the parameters behind the [domain] table of the manifest are readable in the identifier (ldm, avg, nZ, chg, mass, dZ0, and def in a Gilbert-Cameron run):

avg=charge_resolved_chg=wahl_dZ0=false_h=aab3f24b_ldm=BSFG_mass=ame2020_nZ=5

A path among them, a tabulated charge distribution or mass table, appears as the first eight hexadecimal digits of the SHA-1 of its spelling relative to the data directory. Every parameter, the readable ones included, enters h: the same eight digits of the SHA-1 of the canonical text of run_parameters, one section.key=value line per parameter, sorted. A path enters that text relative to the data directory, so the same inputs staged on another machine give the same identifier. metadata.toml records the parameters under [identifier.parameters], and run_identifier recomputes the identifier from them. The identifier is to be compared, never parsed: the parameters of a run are read from its metadata.toml.
